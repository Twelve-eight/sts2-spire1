# sts2-spire1 批判性审查报告（2026-08-25）

> 审查性质：零上下文静态审查。未运行游戏、未构建、未修改任何源码。
> 审查者：ProjectCritic（ox-alpha 子代理）。证据以 `文件路径:行号` 与 git hash 标注；
> 反编译引擎源码参照 `.tmp/dllsrc/`。凡静态无法断言之处均显式标注。

---

## 0. 一句话项目定位

一个基于 BaseLib 的《杀戮尖塔2》(v0.111.x public-beta, Godot/.NET9) 内容模组：把一代的
4 职业 / 305 卡 / 33 遗物 / 49 力量 / 53 事件忠实移植为二代"补充层"，并携带一套相当重的
Harmony 补丁层（联机握手容错、autoslay 冒烟驱动、地图救援、商店守卫）与夜间自动化验证体系，
当前版本 0.9.1（Spire1.json:5），HEAD=`50f8e29`。

## 1. 问题清单（按严重度排序）

### P1-1 商店守卫补丁未做 AutoSlay 门控，改变正常对局的商店行为
- **现象**：`ShopEnoughGoldGuardPatch` 以 postfix 改写 `MerchantEntry.EnoughGold` getter——药水栏满或
  禁药遗物在场时强制返回 false。整个文件没有任何 `AutoSlayer.IsActive`（或 `--autoslay`）检查。
- **证据**：`mod/Spire1Code/AutoSlay/ShopEnoughGoldGuardPatch.cs:32-55`（无门控 + :51 无条件 Info 日志）；
  引擎消费方 `.tmp/dllsrc/MegaCrit.Sts2.Core.Nodes.Screens.Shops/NMerchantPotion.cs:136`
  （价格标签用 EnoughGold 决定 cream/red 着色）、`.tmp/dllsrc/MegaCrit.Sts2.Core.Entities.Merchant/MerchantEntry.cs:76-79`
  （购买失败原因：`!EnoughGold → FailureGold`）。
- **影响**：所有普通玩家（单人+联机）每次进商店都会触发：① 药水栏满时价格显示为红色"买不起"（实际金够）；
  ② 点击购买报"金币不足"而非真实的"药水栏已满"/"禁药"；③ 每个药水槽位评估都写一条 `[Spire1] EnoughGoldGuard:` Info 日志。
  该补丁注释自称是 "Compat fix for the official AutoSlayer shop handler"，却作用于全部对局。
- **修复方向**：方法体首行加 `if (!AutoSlayerImmortalityPatch.Active) return;`（仓库已有现成开关位，
  `Patches/AutoSlayGatePatch.cs:53`）；日志降为 Debug 或仅 autoslay 生效。

### P1-2 联机握手放行默认开启 + 失同步弹窗抑制 = 默认关闭失同步防线
- **现象**：`IgnoreMpModDifferences` 默认 true：ModMismatch 一律放行；同版本号的 ModelID 哈希不符也放行；
  同时前缀拦截 RitsuLib 的失同步诊断弹窗。
- **证据**：`mod/Spire1Code/Config/Spire1Config.cs:59`；`mod/Spire1Code/Patches/MpIgnoreModDiffPatch.cs:44-63`
  （放行逻辑，其日志原文自认 "Serialization safety relies on identical gameplay-mod binaries"）；
  同文件 `RitsuLibPopupSuppressionPatch`（弹窗抑制）；设置界面无此项标签（见 P2-9）。
- **影响**：两个装了不同第三方 mod 集（如一方有 AFTP 另一方没有）的玩家能正常握手开局，中局一旦产生真差异
  （缺内容、模型错位），唯一的用户可见警告被本 mod 自己掐掉，诊断 zip 静默落在 logs 目录无人查看。
  这把引擎设计的三道闸中的两道变成了摆设，且默认值即生效。DEVLOG 已有一次 SLIMED 失同步验尸
  （DEVLOG.md「联机粘液失同步验尸」节），说明该风险不是理论值。
- **修复方向**：默认改 false（出事故的一方主动打开即可复现对方环境）；或在放行的同时保留非阻断性
  HUD 提示（如聊天条/顶栏角标），而不是完全抑制。

### P2-3 LessonLearned 把 Fatal 谓词取反，致命一击条款恒不触发（自认未修）
- **现象**：`shouldTriggerFatal = target.Powers.All(p => !p.ShouldOwnerDeathTriggerFatal())`——引擎默认该谓词
  返回 true（仅 Minion 等覆写 false），官方三张 Fatal 卡均不取反。取反后只要目标身上有任何普通能力，
  `All(!true)` 恒为 false，Fatal 分支死亡。
- **证据**：`mod/Spire1Code/Cards/LessonLearned.cs:30`；反证链 `.tmp/dllsrc/MegaCrit.Sts2.Core.Models/PowerModel.cs:646-649`、
  官方 `dllsrc ...Cards/Feed.cs:38` / `HandOfGreed.cs:49` / `TheHunt.cs:41`；`mod/Spire1Code/Cards/RitualDagger.cs:31-35`
  注释自认 "the mod's own Cards/Feed.cs:28 and Cards/LessonLearned.cs:30 negate the predicate … Not fixed here"。
- **影响**：Lesson Learned（观者稀有）的核心价值"击杀永久升级牌库卡"静默失效，玩家表现为"有时不触发"、极难归因。
  当前观者已归档（Watcher.cs:20-23）使暴露受限，但模型仍注册、旧存档可持有此卡；同病灶 Feed 已退役影响小。
- **修复方向**：去掉谓词前的 `!`，与官方三卡对齐；一行修复 + 一局 autoslay 回归即可。

### P2-4 地图跳过按钮存在三重缺陷（会话内单次失效 / 中文硬编码 / 放行前提未验证）
- **现象与证据**：
  a) 按下后 `b.Disabled = true`（`Patches/SkipNodeButtonPatch.cs:60`），而 Open postfix 见按钮已存在即早退
     （:28-31 不复位 Disabled）；`NMapScreen` 是单例屏（dllsrc `ScreenStateTracker.cs:72` 用 `NMapScreen.Instance`），
     故一次救援后按钮在本会话内永久禁用——第二次卡死无自救可用。
  b) 按钮文案硬编码中文（SkipNodeButtonPatch.cs:37-38），绕过 eng/zhs 双表体系，英文玩家看到中文 UI。
  c) `SetTravelEnabled(true)` 在引擎侧受 `Hook.ShouldProceedToNextMapPoint(_runState)` 二次门控
     （dllsrc `NMapScreen.cs:1273-1277`）：火堆黑屏场景恰是房间收尾卡死，该 hook 是否放行属运行时行为，
     未经验证；DEVLOG 自认"跳过按钮的可视/点击行为需真人局验证"。
- **影响**：这是火堆黑屏这一头号线上事故的唯一缓解措施（DEVLOG 2026-08-25 夜间批次），其自身可靠性直接决定
  用户遇到黑屏时的体验。
- **修复方向**：Open postfix 时重置 Disabled（或改为每次按下可用）；文案走 loc 表；真人复现黑屏验证 c)。

### P2-5 Girya 作为"永远无效"的稀有遗物占据铁甲遗物池
- **现象**：`StrengthBonus` 恒为 0 且没有任何游戏内途径增加（举重 rest-site 选项未实装），BeforeCombatStart
  的 `> 0` 判断使效果永不发生；tooltip 自己承认 "rest-site option not yet wired"。
- **证据**：`mod/Spire1Code/Relics/Girya.cs:13,27-31`；DEVELOP.md:145 自认 STILL OPEN。
- **影响**：玩家在稀有遗物池抽到一个零效果的哑弹，占坑且不可放弃；对"内容忠实移植"的项目定位是直接反例。
- **修复方向**：在实现 rest-site 举重之前把它移入类似 Spire1LegacyPool 的暂存池，或先给固定 +1 力量的近似实现。

### P2-6 N'loth 事件以空壳形态进入共享事件池
- **现象**：两个 relic-offer 全部 withheld，事件只剩"离开"选项。
- **证据**：`mod/Spire1Code/Events/Nloth.cs:26-29`（"NlothsGift is not implementable … so the offers are not shown"）。
  与 DEVELOP.md:9/144 直接矛盾：session 13 已裁定 `CardRarityOdds.RollWithoutChangingFutureOdds` Prefix 可行，
  P2 gap closure 明确列为待办。
- **影响**：共享池（shrines 每幕可刷）里存在一个玩家点进去只能离开的事件，浪费一个事件位并显得未完成；
  同时代码注释与权威设计文档互相打架，误导后续维护者以为"不可实现"。
- **修复方向**：按 DEVELOP §9 的既定方案实现 N'loth's Gift；实现前先不给该事件挂 `Acts` 注册。

### P2-7 文档与现实漂移群（五处，均为可指认的具体矛盾）
1. DEVELOP.md:99（§7a）仍列 `Claw/Chill/Darkness/Equilibrium/MachineLearning` 为"differ mechanically、需要自有类"的陷阱，
   而 `SharedCardReuse.cs:42,51,57,58,60` 已把它们注入复用清单。两边必有一边过时（commit 8781855 大规模扩充复用清单时未回写文档）。
2. DEVELOP.md:101（§7b）宣布"stance API 可行、supersedes the earlier 'stances absent' flag"，但 `Character/Watcher.cs:15-16`
   的 FLAG 仍写着 "no Calm/Wrath/Divinity/Mantra stance API exists in StS2 v0.111.0"。
3. FINAL-REPORT-20260824.md §二.1 描述 Watcher 归档机制为 "`Spire1Config.EnableSts1Watcher=false` 默认"，
   该配置属性已在 commit `0c2ac26` 中删除（现为无开关硬归档，Watcher.cs:19-23）。
4. `Patches/DungeonSelectionPatch.cs:42-44` 注释称 TheCity/TheBeyond/TheEnding "currently ship with empty encounter pools"，
   而 Monsters/Encounters 目录已包含全三幕怪物与遭遇（DEVELOP.md M2 DONE），注释停留在 M2.5 之前。
5. `Character/Spire1LegacyPool.cs:7` 称池内有 "six Strike/Defend variants"，实际 Strike*/Defend*/Bash/Survivor/Neutralize
   均为各职业现役基础牌（PoolScout 全量核对），并不在该池。
- **影响**：本项目高度依赖文档仲裁（DEVELOP.md 自称 Authoritative design + contracts）。漂移会让下一个 worker/
  reviewer 基于错误前提工作——GA 池归属 bug 正是"记忆/文档 vs jar"之争的产物。
- **修复方向**：每处加"截至 commit/日期"标注或直接修正；建立"改清单必回写 DEVELOP §7a/§7b"的纪律。

### P2-8 BaseLib 依赖浮动版本 + 构建自动改写 manifest，与"单一钉死依赖"声明冲突
- **现象**：csproj 用 `Version="*"` 引用 BaseLib 与 ModAnalyzers；`UpdateDependencyVersions` target 还会把
  解析到的版本自动写进 Spire1.json 的 min_version。
- **证据**：`mod/Spire1.csproj:38-39`、`:79-97`（UpdateDependencyVersions）；DEVELOP.md §0 "compile against NuGet 3.4.5"
  的钉死表述；自家 security review 已列为低危未修（DEVLOG.md:485-486 "floating `Version=\"*\"` deps (fix: pin + lock file)"）。
- **影响**：数月后一次干净重建可能编译到 BaseLib 4.x 并把 min_version 抬高，或反向用新 API 编译出对旧运行时不兼容的 dll
  ——这正是项目在 session 6 里吃过的 skew 亏，工具链现状保留了复发通道。
- **修复方向**：钉确切版本 + 提交 lock 文件（自有 review 已给出处方）。

### P2-9 四个新增设置项没有设置界面文案（含两个默认开启的行为开关）
- **现象**：settings_ui.json 只覆盖 7 个旧属性；`PureSts1Pools`(:45)、`DebugShowLocKeys`(:51)、
  `IgnoreMpModDifferences`(:59)、`EnableSkipNodeButton`(:65) 四个属性无 title/hover 键。
- **证据**：`mod/Spire1Code/Config/Spire1Config.cs:45-65` vs `mod/Spire1/localization/{eng,zhs}/settings_ui.json` 全文。
- **影响**：用户在 Mod Settings 里看到的是裸属性名（或缺失项），最需要解释的两个风险开关（联机放行、地图救援）
  恰好零说明；也放大了 P1-2 的"静默改变行为"问题。
- **修复方向**：补两语言 12 条键（title/hover.title/hover.desc × 4）。

### P3-10 zhs 缺 ancients 表，中文玩家看英文建筑师对话
- **证据**：`mod/Spire1/localization/eng/ancients.json`（1333B，THE_ARCHITECT 对 SPIRE1-IRONCLAD/SILENT 的定制台词）

### P3-11 夜间调试注入器把开发机绝对路径编进发布 dll
- **证据**：`Patches/DebugCardInjectPatch.cs:21`、`Patches/DebugRelicInjectPatch.cs:25`

- **修复方向**：`#if DEBUG` 或条件编译排除；至少移到配置常量并在发布构建断言为空。

### P3-12 关键过程资产放在 gitignored 的 .tmp/ 里
- **证据**：`.gitignore:2` 忽略 `.tmp/`；而 DEVLOG 反复称 `.tmp/night/coverage.js`、"固化脚本 `.tmp/audit-event-vars.js`"
  为权威覆盖计算器/审计工具；现场日志已被轮转丢失一次（DEVLOG 火堆黑屏节："原始 110k 行现场日志已被轮转丢失"）。
- **影响**：方法论沉淀（WORKPLAN §3 明确要技能化）建在最易丢失的目录上；换机/清缓存即失传。
- **修复方向**：把确需长存的脚本移入 research/tools/ 或 .omp/skills/ 并入库。

### P3-13 MainFile 补丁注册循环在 GetTypes() 层面仍是单点
- **证据**：`MainFile.cs:42-58`：逐类 try/catch 只保护 CreateClassProcessor.Patch() 阶段；
  `typeof(MainFile).Assembly.GetTypes()` 若因任何类型加载失败抛 ReflectionTypeLoadException，循环整体中断，
  所有补丁（含逐类加固本身）都不会应用。[静态可断言的异常路径，触发概率取决于程序集完整性]
- **修复方向**：包一层 try/catch 降级为 `e.Types.Select(t => t)` 过滤 null 再继续。

### P3-14 autoslay 冒烟跑在"dev 模式"的游戏上，覆盖≠发布体验
- **证据**：`Patches/AutoSlayGatePatch.cs:19-30` 全进程翻转 `IsReleaseGame()`；引擎中该开关还控制：
  EA 免责声明跳过（dllsrc `NMainMenu.cs:493`）、图鉴按钮常显（`NPauseMenu.cs:269`）、Epoch Ctrl 键解锁
  （`NEpochSlot.cs:350`）、教程重置入口（`NResetTutorialsButton.cs:65`）、SaveManager 分支（`SaveManager.cs:1122`）。
- **影响**：8 胜 0 崩的冒烟矩阵验证的是 dev-mode 构建；release 路径的若干 gating 从未被冒烟覆盖。
  属已知代价（无其他自动化途径），但应记录在案。
- **修复方向**：接受现状但在 WORKPLAN/DEVLOG 记一句"冒烟=dev mode"；或把关键 release-path 检查列入人工清单。

### P3-15 manifest 允许最低游戏版本 0.107.0，低于实测目标 0.111.x
- **证据**：`mod/Spire1.json:6` (`min_game_version: "0.107.0"`) vs DEVELOP.md:10（Target v0.111.0）。
- **影响**：老 beta 版本可安装本 mod，而全部 Harmony 目标签名/私有字段均只对 0.111.x 取证过，低版本行为未定义。
- **修复方向**：抬高到实测过的最低版本。

### P3-16 复用清单的"逐字段核验"声明被抽样证伪
- **证据**：`SharedCardReuse.cs:17-19` 声明 "Every entry below was verified field by field"；
  但 :147 给 `ToolsOfTheTrade` 的注释是 "0E, 6 dmg (+3)"，而 KB 权威条目为 POWER/RARE
  （`research/sts1-kb/cards-green.json:1355-1362`）——注释连卡牌类型都错了。
- **影响**：单点错误不影响运行（注入的是 StS2 原生卡对象），但它证明这些注释并非核验记录而是事后装饰，
  后续维护者不能再据此信任清单；真正的数值一致性目前只有个案级验证（BladeDance、Deflect 等）。
- **修复方向**：以 KB 为源生成 reuse 清单（脚本化 diff），让声明重新可信。

### P3-17 Thunderclap jar 归属复核悬空
- **证据**：WORKPLAN-20260825.md §2.2（"grep 大小写问题待核"）；`.tmp/legacy-audit.json` `"notInJar": ["Thunderclap"]`。
- **影响**：功能无恙（复用 StS2 原生 Thunderclap，SharedCardReuse.cs:80），但审计清单挂着一条未闭环项，
  且它恰好出现在"jar 清单完整性"这个 KB 数据质量的敏感点上。
- **修复方向**：一次 javap 复核即可闭环。

## 2. 覆盖维度结论

| 维度 | 结论 |
|---|---|
| **代码正确性风险** | 中低。306 个卡牌文件池归属全量交叉验证零误标（GeneticAlgorithm 历史 bug 已修，af6d1d7）；发现 1 个行为级 bug（P2-3 Fatal 谓词）+ 2 个未门控副作用补丁（P1-1、部分 P2-4）。Harmony 层防御意识好：per-type try/catch 防 PatchAll 连坐（MainFile.cs:38-56）、fail-safe 默认明确注释。 |
| **并发/联机安全** | 最薄弱维度。RewardClamp/Splash/DustyTome 三补丁经自查均为 per-player 上下文（DEVLOG「联机兼容审计」节，抽查属实）；但 P1-2 的默认放行+弹窗抑制实质上关闭了失同步防线，skip 按钮的 IsTravelEnabled 出现在引擎网络属性序列化表中（dllsrc NMapScreen.cs:2753,2803,2853），其跨端语义未经运行时确认。 |
| **资源泄漏** | 低风险。RestSiteBackgroundPatch 每次进火堆新建 Control 树替换引擎返回值（Patches/RestSiteBackgroundPatch.cs:36-58），旧场景是否释放由调用方决定，纹理走 ResourceLoader 缓存无泄漏；未见集合无限增长模式。细节需运行时确认（§5）。 |

## 3. 最可能出事故的三件事

1. **联机真差异静默失同步**（P1-2 × P2-9）：默认放行握手 + 抑制 RitsuLib 弹窗 + 设置页零说明——
   两名 mod 集不同的玩家顺利开局、中局崩坏、双方都没有可见线索，诊断 zip 躺在 logs 里无人知晓。
   DEVLOG 的 SLIMED 案例证明这类分歧真实发生。
2. **火堆黑屏救援链二次失效**（P2-4 × 火堆根因未明）：黑屏是当前唯一未定位的线上故障；缓解按钮
   会话内单次失效、放行前提 `Hook.ShouldProceedToNextMapPoint` 在卡死状态下是否放行未验证——
   下次黑屏很可能连自救都失败。
3. **游戏版本升级引发补丁静默失效潮**（P3-14/P2-8 的叠加态）：补丁层大量依赖私有成员反射
   （`_keywords` 字段、`RecalculateTravelability`、`_screenHandlers`、`_mockGeneratedCard`）与 IL 字面量
   transpiler（`Ldc_I4_S 49→120`），BaseLib 又是浮动引用——一次 0.112 更新可同时折断多处，
   而 per-type try/catch 会把它们变成"功能悄悄消失"而非显性崩溃。
